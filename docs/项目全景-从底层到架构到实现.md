## 一、项目概述与演进时间线

RAG-KnowledgeBase 是一个自研的检索增强生成（RAG）知识库问答系统：文档丢进去，问题问出来，回答必须带来源、没有依据就拒答。两种形态共享同一套引擎：

| 形态 | 入口 | 场景 |
|------|------|------|
| Streamlit 单机版 | `streamlit run streamlit_app/app.py` | 个人本地使用 |
| Web 多用户版 | `python -m web_app.backend.dual_app`（用户站 4010 / 管理站 4011） | 多账号、按用户隔离知识库、管理后台 |

**演进时间线**（每阶段都由具体问题驱动，而非预设的大规划）：

| 时间 | 阶段 | 标志性产出 |
|------|------|-----------|
| 初期 | MVP | Streamlit 五页 + 向量检索 + 本地模型全离线 |
| 中期 | Web 化 | FastAPI 双端口、MySQL 账号体系、多用户知识库隔离、云端模型（硅基流动） |
| 2026-08-15 | 第一轮体检 | 评估 72/100，P0-P3 问题清单；自建 32 条评测集 |
| 2026-08-16~17 | 加固与扩展 | FAISS 写锁（P0）、12 种格式统一解析、OCR 二层回退、全链路风险修复 H3+M7+L9、评测集独立化（104 条） |
| 2026-08-17 | 质量标定 | 嵌入升级 bge-m3（1024 维）、上下文窗口 4000→10000、阈值标定（重排概率是唯一可靠判别） |
| 2026-08-18 | 应用层补全 | 前端功能（高级检索面板/会话搜索批量/改密/反馈闭环/好差评页）、JWT 过期检查、CDN 本地化 |
| 2026-08-19 | 权威评测与上线 | 824 条权威公开数据基准 + 端到端六指标 + 阈值敏感性；部署至服务器，博客文档同步 |

## 二、底层：存储与模型层

### 2.1 三级存储

```
┌─ 向量索引 ────────────────────────────────┐
│ FAISS（每用户独立目录）                     │
│ data/web/users/<uid>/knowledge_db/        │
│   ├── faiss_index/index.faiss + index.pkl │
│   ├── bm25_index.v3.pkl / bm25_docs.v3.pkl│  ← 分词器版本化，改分词规则自动失效重建
│   ├── documents_metadata.json             │
│   ├── original_files/（原件，重建的源头）   │
│   └── .faiss_write_lock（跨进程文件锁）     │
├─ 关系数据 ────────────────────────────────┤
│ MySQL：users / sessions / app_settings    │
│       / llm_api_presets / 审计日志系列表   │
├─ 前端状态 ────────────────────────────────┤
│ localStorage（会话/偏好）⇄ 云端同步兜底    │
└───────────────────────────────────────────┘
```

设计要点：
- **每用户物理隔离**：`path_context` 把"当前用户"绑定为进程级上下文，所有 FAISS/BM25/原件读写都落在该用户目录，杜绝越权。
- **BM25 索引文件带分词器版本号**（v3）：分词规则一改，旧 pickle 自动失效重建——否则会出现"旧索引 + 新分词"的静默错配。
- **原件永远保留**：任何索引层升级（如换嵌入模型）都能从 original_files 整体重建，这是所有"重建红线"成立的前提。

### 2.2 FAISS 并发写安全（P0 修复）

**遇到的问题**：多线程/多进程同时入库时 FAISS 索引损坏——两个写者同时读到同一基线、各自追加、后写覆盖先写，向量静默丢失。

**改进**：两级锁（`utils/faiss_write_lock.py`）：
1. 进程内 `threading.RLock`（可重入，深度计数，最外层才碰文件锁）；
2. 跨进程文件锁：POSIX `flock` / Windows `msvcrt.locking` 轮询，锁文件放知识库根目录（避免被 `rmtree(faiss_index)` 误删）。

**效果**：10 文件 × 6 线程并发混合格式入库 0 失败（2026-08-19 压测）；5 个专项单测覆盖重入/线程/跨进程互斥。

### 2.3 模型层与那条最重要的红线

| 角色 | 本地 | 云端（硅基流动，现役） | 备注 |
|------|------|----------------------|------|
| 嵌入 | BAAI/bge-small-zh-v1.5（512 维） | **BAAI/bge-m3（1024 维）** | 维度=索引维度，**不可混用** |
| 重排 | bge-reranker-base CrossEncoder | **BAAI/bge-reranker-v2-m3** | 概率输出直接与阈值同尺度 |
| OCR | Tesseract chi_sim+eng | DeepSeek-OCR（限免） | 二层回退 |
| LLM | Ollama | DeepSeek / 任意 OpenAI 兼容 | 管理端多预设 |

**踩过的坑**：文档里默认的 `bge-small-zh-v1.5` 和 `bge-reranker-base` 在硅基流动**根本不存在**（API 400 Model does not exist）——是拿真实 key 逐个调 `/v1/models` 才发现的。教训：模型配置不能只信文档，要实测清单。

**红线**：bge-m3 是 1024 维，旧 512 维索引与之不兼容；切换嵌入模型必须**删旧索引、从原件整体重建**，混用 = 检索结果随机错乱且无报错。

### 2.4 OCR 二层回退

```
图片/扫描 PDF
  → 本地 Tesseract（chi_sim+eng，跨平台自动探测可执行路径）
  → 识别质量不满意（手写/复杂表格/公式）→ 云端 DeepSeek-OCR
     提示词: "<image><|grounding|>Convert the document to markdown."
     输出清洗: 剥离 <|ref|>…<|det|>[[坐标]] 标注（真实 API 调试发现）
```

三档模式（off / fallback / always）由管理端配置。本地层缺语言包时自动全走云端，不阻塞上传。

## 三、中层：检索与对话引擎

### 3.1 检索管线全景

```
用户输入
  → 意图识别（闲聊直答 / 走 RAG）
  → 查询类型分类（事实/概念/程序…）→ 决定 fetch_k 与偏好块层级
  ┌──────────────── 混合召回 ────────────────┐
  │ 向量：FAISS L2 → 1/(1+d) 相似度           │
  │ BM25：jieba 分词 + 词覆盖率门控            │
  │ 融合：RRF(k=60) 定序；证据分=max(向量, BM25归一分) │
  │ 地板：向量 max<0.5 且 BM25 无命中 → 返回空  │
  └──────────────────────────────────────────┘
  → CrossEncoder 重排（宽召回 k×4 → 概率排序）
  → SIMILARITY_THRESHOLD 过滤（低于 0.3/0.4 丢弃）
  → 无过线者：低分回退保留 3 条（不硬拦，交给 LLM 层）
  → 父块扩展（small→medium）+ 同文档去重
  → max(k, 8) 截断 + 10000 字符累加截断
  → 编号上下文 [来源N] → LLM 生成 / 拒答
```

### 3.2 管线里每个"奇怪设计"的由来（问题→改进→效果）

这张表是整个项目的方法论核心——**每个环节的设计都是被一个具体的失败案例逼出来的**：

| # | 遇到的问题 | 根因 | 改进 | 效果 |
|---|-----------|------|------|------|
| 1 | 评测 nDCG > 1（数学上不可能） | 同文件多个 chunk 占满 top-k，DCG 重复计分 | 召回列表按文件名去重保序 | nDCG 回到 [0,1]，多相关文档的 Recall 不再被虚假压低 |
| 2 | 查询"黑洞的信息悖论"靠"信息"一词拿到 BM25 满分 | 弱词重叠穿透：单字/虚词也能产生高分匹配 | BM25 词覆盖率门控：覆盖率≥50% 且至少一个多字词命中，疑问虚词入停用词 | 混合检索负样本误召回从"几乎全漏"降一个数量级 |
| 3 | 门控漏检：查询"逾期"匹配不上文档 token"逾期费" | 门控用 token 相等比较，分词边界不一致 | 改为**原文子串匹配** + 分词器升 v3（索引自动失效重建） | 边界词命中正常 |
| 4 | 混合检索分数无绝对含义，与阈值不同尺度 | RRF 分数只定序不定量 | 证据分 = max(向量相似度, BM25 归一分)，与绝对阈值同尺度 | 阈值判定有了统一基准 |
| 5 | 重排 API 偶发失败导致整次检索空结果 | 异常直接上抛 | rerank 失败**保序保分回退**（fallback_scores），绝不产生伪高分 | 云端 503 时链路不断，检索质量退化为混合召回而非报错 |
| 6 | 正负样本分数重叠，0.5 阈值切不开（0815 标定） | 向量分数正负重叠（正 0.62-0.68 vs 负 0.41-0.47） | 标定结论：**重排概率是唯一可靠判别**（正 p25=0.85 vs 负 <0.25）；向量分数只做廉价预过滤 | rerank 默认开启写进 rag_defaults |
| 7 | BM25 首查卡顿数十秒 | 索引惰性构建在首个请求内完成 | 入库后后台线程预热（捕获 kb_dir、线程内重绑用户上下文） | 首查延迟恢复正常 |
| 8 | 预热线程读错用户目录 | `contextvars` 不跨 `threading.Thread` 传递 | 线程内显式 `set_user_kb_context` | 多用户下预热不再串目录 |
| 9 | 陷阱问题（"心肺复苏的唐诗描写"）检索层拦不住 | 语义欺骗：词形全命中、语义无关 | 承认检索层拦不住，**双层防线**：低分回退 + LLM 提示词强约束拒答 | 20 条陷阱负样本拒答正确率 0.980 |
| 10 | 长文档答案被 4000 字符上下文截断 | 上下文窗口保守 | 4000→10000，k 5→8 | 端到端 Correctness 0.938（对人工标准答案） |
| 11 | 前端 Markdown 渲染时好时坏 | vendor 脚本相对路径在两个站点解析成不同 URL，404 后静默降级纯文本 | 绝对路径 `/static/vendor/`（19 页） | 部署服务器时实测发现并修复 |

### 3.3 对话层

- **流式 NDJSON**：`meta`（模式/检索语/来源）先行 → `chunk` 流式正文 → `done`；前端断线/关页时为未完成的助手回合写入"已中断"标记，可重试。
- **意图识别**：轻量分类器区分闲聊/RAG，闲聊不走向量库（省一次嵌入+检索）。
- **来源溯源**：`[来源n]` 前端转可点击——有 URL 新开标签，否则展开检索块中对应片段。
- **多轮**：历史压缩进 prompt；检索语与原句不一致时在 meta 里展示"检索用语"（查询重写透明化）。
- **即时文档通道**：与知识库完全隔离——全文进上下文（上限 10 万字符）、不走向量库，适合"一次性文档快问快答"。

### 4.1 代码分层（双形态复用同一引擎）

```

streamlit_app/               ← 单机 UI（薄壳，调同一套 services）
```

### 4.2 服务器部署拓扑（106.52.75.171）

```
外网 :80 / :4010 / :4011
   │
   ▼
nginx（三站点统一 auth_request → :9001 auth-service SSO 网关）
   │  :4010 → 127.0.0.1:14010 ┐
   │  :4011 → 127.0.0.1:14011 ┤→ rag-service（systemd，dual_app 双端口）
   │  :80  → ~/blog/public（Hugo 静态站）
   ▼
MySQL（账号/会话/app_settings/预设/审计）
```

运维要点：
- 应用只绑回环，公网入口全收在 nginx + SSO 后面；
- 服务器连不上 GitHub，代码更新走 **git bundle 中转**（本地 `git bundle create` → scp → `git fetch <bundle> && reset --hard`）；
- venv 必须有 `cryptography`，否则 MySQL 8 的 caching_sha2 认证连不上（重启后服务起不来的隐形炸弹，已装）。

### 4.3 配置体系（两级）

| 层 | 存储 | 生效方式 | 内容 |
|----|------|---------|------|
| 静态 | config.json（gitignored） | 重启 | 密钥、MySQL、模型默认值 |
| 动态 | MySQL `app_settings` | 免重启 | LLM 预设、检索默认值、分块层级、开关、限流、向量 provider、上传格式/限额 |

## 五、质量保障体系

### 5.1 测试

**99 项 pytest**：解析器 22 / 全链路修复回归 20 / 硅基流动客户端 15（mock）/ 查询分类 20 / 检索纯函数 11 / 分数归一化 6 / FAISS 写锁 5。CI（GitHub Actions）每次推送自动跑。

### 5.2 评测的三次演进（评测哲学的变化）

| 代 | 规模 | 语料 | 负样本 | 暴露的问题 |
|----|------|------|--------|-----------|
| v0 | 32 条 | 自建 13 篇 | 少量 | 发现 nDCG>1（同文件重复计分） |
| v1 | 104 条 | 自建 10 篇（7 领域 4 格式） | 19 条（6 陷阱） | 标定出"重排是唯一防线"；但**自己出题自己阅卷**，天花板虚高 |
| v2 | **824 条** | **DuReader-retrieval（百度 ACL2022）+ CMRC 2018（人工标注）+ 维基长文 + 自建** | 78 条（34 纯负自动撞词裁剪 + 25 陷阱） | 权威数据下测出真实水位与弱项 | 

v2 构建全流程可复现（`scripts/build_eval_dataset_v2.py`：HF 镜像下载→转换→自检→`EVAL_SET_V2.json`），负样本的"纯负"会自动校验关键词不在语料中，撞词即裁。

### 5.3 指标体系（四层）

1. **检索层**：Recall@k/@3、nDCG@k、MRR、FalseRecall（负样本误召回率）、Balanced（召回与特异度调和平均）、top-1 分数分布（标定阈值用）；
2. **生成层（RAGAS 风格 LLM-as-judge）**：Faithfulness / Answer Relevancy / Context Precision / **Answer Correctness（对权威标准答案）** / **Context Recall（GT 要点被上下文覆盖）** / 拒答正确性；
3. **性能层**：检索/生成延迟 p50/p90；
4. **稳定性层**：并发入库、超长文档、全量 pytest。

四种检索口径：`vector` / `hybrid` / `rerank`（严格阈值） / **`prod`**（直接调生产 `retrieve_for_rag` 全管线）——评测口径与生产口径的差值本身就是发现（见 5.4）。

### 5.4 权威基准下的最终水位（2026-08-19）

| 维度 | 结果 | 备注 |
|------|------|------|
| Recall@5（生产管线） | **0.989** | 语料 10→155 文档（×38），仅降 0.4pt |
| 误召回（重排严格） | 11.5% → 阈值 0.4 后 **5.1%** | 阈值敏感性重放：正样本存活仅降 0.7pt |
| Faithfulness | **0.995** | |
| Answer Correctness / Context Recall | **0.938 / 0.957** | 对 CMRC/维基人工标准答案 |
| 拒答正确性 | **0.980** | 20 条陷阱负样本 |
| 检索/生成延迟 p50 | 2.2s / 2.0s | 云端重排往返占大头 |
| 分来源召回 | CMRC 0.996 / DuReader 0.992 / 维基长文 1.000 / 自建旧 0.982 / 自建新 **0.929** | 弱项=表格/参数类细粒度查询 |

**一个关键的口径发现**：`prod` 模式负样本"误召回"73%，其中 48 条是低分回退的设计行为（无结果过阈值时保留 3 条低分片段，top1 分≈0）——生产形态下检索层**故意不硬拦**，防线交给 LLM 拒答层，而拒答实测 0.980 证明双层防线成立。这解释了为什么"看起来误召回很高"的系统实际幻觉率极低（Faithfulness 0.995）。

## 八、一页总结

**这个项目验证的三件事：**

1. **质量是测出来的，不是感觉出来的**——从 32 条自建题到 824 条权威公开基准，每次换更难的尺子都暴露新问题（nDCG 虚高→弱词穿透→口径差异），每次修复又有回归测试和评测基线兜底。
2. **检索层和生成层各司其职**——检索层追求"找得到"（混合召回）+"分得清"（重排），不追求"拦得住"（硬陷阱天然拦不住）；生成层负责"不编造"（拒答）。双层防线的分工是实测出来的，不是设计出来的。
3. **工程红线比功能重要**——嵌入维度不可混用、索引必须可重建（原件保留）、写锁必须跨进程、失败必须可回退。这些不出事时看不见，出事就是数据损坏。
