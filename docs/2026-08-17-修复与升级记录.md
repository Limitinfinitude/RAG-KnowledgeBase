## 一、改动前的架构概况

```
上传 → 文件解析 → 多层级分块(smart_chunker) → FAISS 入库(+BM25 索引)
                                                    │
问答：查询 → 意图分类 → (指代改写) → 查询分类 → 混合检索(BM25+向量+RRF)
      → 分数归一化 → CrossEncoder 重排 → 父块扩展 → 上下文裁剪(4000字符)
      → LLM 生成 → 来源溯源对齐 → 流式返回
```

- **双端形态**：Streamlit 单机版 + FastAPI Web 多用户版（4010 用户端 / 4011 管理端），共享核心引擎
- **用户隔离**：`utils/path_context.py` 用 contextvars 按请求绑定各用户的知识库目录（`data/web/users/<id>/knowledge_db/`）
- **模型**：本地 bge-small-zh-v1.5 嵌入（512 维）+ bge-reranker-base 重排；可切换硅基流动云端嵌入/重排（密钥存 MySQL `app_settings`）

此前评估（72/100）留下的 TODO 清单中，本次完成了全部 P0 项，并按需扩展了格式与 OCR 能力。

## 二、改动一：P0 并发写安全（FAISS 写锁 + LLM 配置上抛）

### 发现的问题

**P0-1 FAISS 并发写不安全。** 排查后发现真实缺口与最初评估描述不同：
- 上传入库其实已由 `ingest_queue` 的单 worker 线程序列化（不是风险点）；
- 真正的缺口是**三个写入口互不互斥**：用户删除文档（FastAPI 线程池执行）、管理员重置索引、与入库 worker 可能同时「改内存 + `save_local()`」同一用户的索引文件。`save_local` 直接覆盖 `index.faiss/index.pkl`，交错写入会把索引写坏。
- 另有内存态竞态：写路径与检索路径共享 `vdb_cache` 里同一个 FAISS 对象，原地修改会污染正在进行的检索。

**P0-2 `build_chat_llm` 静默吞异常。** 配置读取失败时返回空 API key 的 `ChatOpenAI`，错误推迟到对话调用时才爆 401，难以排查。

### 修改内容

1. 新增 `utils/faiss_write_lock.py`——按知识库目录的两级写锁：
   - 进程内 RLock（同线程可重入，删除的回退路径里再调 `get_vector_db` 不死锁）；
   - 跨进程文件锁 `.faiss_write.lock`（POSIX flock / Windows msvcrt），`uvicorn --workers N` 场景也安全。锁文件放知识库根目录而非 `faiss_index/` 内，避免重置索引时删掉正在持有的锁。
2. 五个写入点的「改内存 + save_local」全部包进同一临界区：`db.py`（加载/初始化）、`file_loader.py`、`ingest_streaming.py`（流式全程含周期性落盘）、`document_deleter.py`（删除主路径+回退重建）、`admin_vector_ops.py`（管理员重置）。
3. 入库与删除改用**私有 vdb 副本**（`ingest_queue.py`、`rag_routes.py`），写完 `bump_user_cache` 让检索自动重载，消除内存态竞态。
4. `services/llm_factory.py`：配置读取失败记 `logger.exception` 并抛带原因的 `RuntimeError`；model/api_key/base_url 任一缺失直接报「配置不完整」并指引到管理端配置页（所有调用方均已有 try/except 或规则回退，行为安全）。

### 目的

两用户同时操作（一边上传、一边删除）时索引不损坏；配置错误在构造时暴露而不是调用时爆 401。

### 结果

- 新增 `tests/test_faiss_write_lock.py` 5 个测试：重入、线程互斥、超时、**真实子进程跨进程互斥**（本机走 msvcrt 分支，服务器走 flock 分支）、不同目录不互斥——全过。
- 过程中修了一个实测发现的 bug：`RLock.acquire(timeout=None)` 在 CPython 抛 TypeError，改为不传超时参数。
- 全量测试通过；FakeEmbeddings + 真实 FAISS 走通「加锁初始化 → add → 加锁落盘 → 加锁重载」全链路。

## 三、改动二：上传格式扩展 + 解析入口统一

### 发现的问题

- **四套各自为政的解析实现**：`file_loader.py`（入库）、`instant_document_loader.py`（Streamlit 即时对话）、`instant_doc_parse.py`（Web 即时对话）、`document_preview.py`（原文查看）各有独立 elif 链，加一种格式要改 4-5 处，行为逐渐发散（如即时对话不支持 Excel、Web 即时只支持 4 种格式）。
- **`.doc` 假支持**：白名单里有但 python-docx/docx2txt 都读不了老版二进制格式，报「未提取到文本内容」误导用户。
- **不支持的扩展名静默返回 0 块**：上传任务显示"成功"但什么都没入库。
- 支持格式仅 7 种，缺 PPT/CSV/HTML/图片。

### 修改内容

1. 新增 `utils/document_parsers.py` 统一解析注册表：`PARSERS = {扩展名: 解析器}`，签名统一 `(temp_path, original_name) -> List[Document]`。四处调用方全部切换，编码探测收敛为一份（`detect_text_file_encoding`）。
2. 新增解析器：**PPTX**（文本框+表格+演讲者备注，按「幻灯片 N」分段，新增依赖 `python-pptx==1.0.2`）、**CSV**（编码探测支持 BOM/GBK）、**HTML**（剥 script/style、保留标题、压缩空行）。
3. `.doc` 移出默认白名单，仍上传时给出定向指引（「请另存为 .docx」）；不支持的扩展名从静默 0 块改为明确报错。
4. `file_type` 元数据统一为实际扩展名（原 xlsx/xls 都标 "excel"，确认无下游消费）；流式入库的编码探测复用统一实现。
5. 白名单默认值、Web 前端 accept（kb.html / instant.html）、Streamlit 三处 type 列表同步更新；`requirements*.txt` / `environment.yml` 更新（移除未用的 docx2txt，加入 python-pptx）。

### 目的

支持课件/表格/网页存档等高频知识库内容；「加格式只改一个文件」，终结解析逻辑发散。

### 结果

- 新增 `tests/test_document_parsers.py` 11 个测试（含白名单一致性校验：`_DEFAULT_EXT == SUPPORTED_EXTENSIONS == INSTANT_ALLOWED_EXT`，防止三处再漂移）。
- 端到端验证：pptx 6 块 / csv 4 块 / html 11 块真实入库（解析→分块→加锁写 FAISS→元数据落盘→原文存档→预览提取）全链路通过；净删约 320 行重复代码。
- 行为修正：Web 即时对话从 4 种格式扩到 9 种；扫描版 PDF 在即时对话路径也能走 OCR 了。

## 四、改动三：OCR 体系升级（跨平台 + 双语 + 图片 + 云端二层回退）

### 发现的问题

1. `config.py` 的 `TESSERACT_CMD` 硬编码 Windows 路径，Linux 服务器上 OCR 一调用就挂（评估清单 P2 项）。
2. 固定 `lang="chi_sim"` 单语言，英文混排识别差；且语言包写死，缺包环境直接报错。
3. 没有图片直传入口（截图/扫描件无法入库）。
4. Tesseract 对手写、复杂表格、公式天花板明显。

### 修改内容

1. **跨平台路径解析**（`config.py`）：环境变量 `TESSERACT_CMD` → `config.json ocr.tesseract_cmd` → `shutil.which("tesseract")` → 常见安装路径兜底 → None（给出带安装指引的明确报错）。服务器从此可用。
2. **语言包自动探测**（`resolve_ocr_langs()`）：查一次 `--list-langs` 并缓存，两个都有用 `chi_sim+eng`，缺哪个降级哪个，探测失败回退默认组合。
3. **图片入库**：jpg/jpeg/png 加入白名单与全部前端，`parse_image` OCR 后与普通文档同链路。
4. **云端二层回退**（本次核心）：
   - `utils/siliconflow_client.py` 新增 `SiliconFlowOCR`：`POST /v1/chat/completions`（`image_url` base64 + DeepSeek-OCR 官方 `<|grounding|>` markdown 提示词，按硅基流动文档查证），输出自动剥 `<markdown>` 包裹与坐标标注（实测发现标注会污染向量块）。
   - `utils/document_parsers.py` 新增 `_ocr_image()` 策略：本地 Tesseract 单次 `image_to_data` 同时取文本与平均置信度；**置信度 < 阈值(60) 或文本 <10 字或本地报错**（手写/表格/公式的典型表现）时该页升级云端；云端失败保留本地结果，**永不因回退丢内容**。三条 OCR 路径（常规 PDF / 流式大 PDF / 图片）统一接入，按页判断，清晰页不烧 API。
   - 配置存 MySQL `app_settings`（60 秒进程内缓存）：`ocr_cloud_mode`（off/fallback/always）、`ocr_cloud_model`（默认 `deepseek-ai/DeepSeek-OCR`，可换任何 OpenAI 视觉格式模型如 Qwen-VL）、`ocr_cloud_conf_threshold`。密钥复用已配置的 siliconflow provider，**无密钥自动视同 off，未配置的部署零影响**。
   - 服务器不装 Tesseract 也能跑图片/扫描件（本地层缺失时自动全走云端）。

### 目的

免费本地层覆盖清晰扫描件；限免期的 DeepSeek-OCR 兜底手写/表格/公式等硬场景；限免结束后切回 fallback 即恢复省成本模式。

### 结果

- 本地真图测试通过（`HELLO RAG 2468` 双语识别）；空白图正确报「未识别到文字」。
- **用真实密钥端到端验证**：模型 ID `deepseek-ai/DeepSeek-OCR` 在硅基流动可用，生成测试图 → 云端准确识别（`RAG Evaluation Report / Recall@5 = 0.87`），grounding 坐标标注清洗后输出纯净、表格 markdown 结构保留；同一图在 fallback 模式下高置信度自动留在本地层。
- 回退策略 8 个 mock 单测 + OCR 客户端 7 个单测全过。

## 五、改动四：全链路风险修复（H 高危 3 + M 中危 7 + L 低危 9）

对检索→重排→上下文→对话全链路做了一次系统审查（探索代理通读 + 关键发现人工复核），按严重程度全部修复。

### 高风险

**H1 BM25 预热线程跨用户污染（数据泄漏级）**
- 问题：`ingest_queue` 在后台线程重建 BM25，`threading.Thread` 不继承 contextvars，`save_bm25_index` 的 `get_kb_dir()` 落到默认 Streamlit 目录——Web 用户的 BM25 索引覆盖 Streamlit 知识库，**Streamlit 混合检索会返回别的用户的文档正文**。
- 修复：调度时捕获 kb 目录；线程内显式重新绑定用户上下文；从磁盘重载最新 FAISS（持写锁）而非复用内存快照（同时解决 M6 旧快照写回）；索引已存在则跳过；per-user 防并发重入。附带修复：删除文档路径此前不失效 BM25（已删文档仍可被关键词检索），现已接入同一失效+预热流程。

**H2 向量地板一票否决整个混合检索**
- 问题：向量最高分 < 0.5 直接 `return []`，BM25 精确命中（专有名词/型号——混合检索的目标场景）被一起丢弃。
- 修复：双信号判定——向量低于地板 **且** BM25 无命中（原始分全 0）才判「无相关内容」；BM25 有命中则继续融合。负样本防线保留（负样本两路皆空）。

**H3 分数单位混用（0.3/0.5 阈值语义翻转）**
- 问题：单知识库 hybrid 未开重排时融合分是 RRF 原始量级（~0.01），`SIMILARITY_THRESHOLD=0.3` 永不满足 → 永远走低质量回退 + `max_score<0.3` 恒真 → 每次都进 rag_low_score 提示词分支；而「全部知识库」多 KB 分组的 min-max 归一化又把无关结果最高分拉到 1.0，低置信防线失效。这是此前评测中部分查询「满分假象」的直接成因之一。
- 修复：混合检索返回**证据分**（0-1，= max(该文档向量相似度, BM25 归一分)），RRF 只决定排序不作为分数——返回分数与绝对阈值恢复同尺度可比。

### 中风险

| # | 修复 |
|---|------|
| M1 | RRF 融合标识从 `id(doc)`（pickle 副本必然不同 id，同块永不融合、重复占位）改为 `source_file + 内容哈希` |
| M2 | Web 端 reranker 从「每请求重载模型 + 在事件循环内同步执行 + 失败静默」改为进程级缓存（按 provider/model/base_url）+ `asyncio.to_thread` 构造 + 失败记日志；顺带删除 `utils/embedding.py` 里无人调用的重复 `get_reranker` 副本 |
| M3 | rerank 失败不再伪造 1.0 递减高分（会绕过阈值与低置信防线）：`rerank_documents` 沿用原始检索分，`SiliconFlowReranker` 失败上抛 |
| M4 | 意图分类「怎么使用」等子串误伤知识库问题（「灭火器怎么使用」被当闲聊跳过检索）：用法短语须与系统指代词（你/系统/助手/平台/知识库）共现才判 CHAT |
| M5 | 父块扩展后按内容哈希去重（多个 small 子块扩展到同一 medium 父块时不再重复占用上下文名额） |
| M6 | （并入 H1）预热从磁盘重载最新索引，防旧快照写回 |
| M7 | BM25 分词保留单字 CJK（非虚词），单字查询/单字型号不再静默无关键词；索引文件名升版 `bm25_index.v2.pkl`，旧 pickle 自动失效重建 |

### 低风险

L1 `smart_chunker` logger 未定义（LLM 摘要失败时 NameError）；L2 指代词「其/该」单字误匹配（其中/其他/该死）改为完整词，rephrase 静默失败补日志；L3 OllamaReranker 标记为遗留实现并告警（分数从自由文本抓数字，不可靠）；L4 CUDA 判定改 `torch.cuda.is_available()`；L5 限流桶总数上限 + 过期清扫；L6 元数据读取加 mtime 缓存（一次检索原本多次全量读 `documents_metadata.json`）；L7 问候语前缀匹配加词边界（"hipaa"不再被当"hi"）；L8 `finalize` 尊重调用方传入的 k（多子查询的 k_sub 终于生效，不再钉死 5）；L9 `list_indexed_source_files` 失败告警而非静默空列表。

### 结果

- 新增 `tests/test_retrieval_fixes.py` 16 个回归测试（融合/地板/分词/意图/重排回退/去重/预热线程），全量 **95/95 通过**；13 个改动模块导入冒烟通过。
- **部署注意**：BM25 索引文件名升版，服务器上旧 `bm25_index.pkl` 会在首次混合检索时自动重建（大库首次会慢一次，属预期）。建议部署后重跑 `scripts/eval_retrieval.py` 验证分数语义修正后的指标变化。

## 六、改动五：评测数据集扩充与全链路实测（2026-08-17）

### 数据集
- 新增 8 个跨领域自建语料（睡眠/运动/理财/高铁/图书馆/咖啡/智能音箱），刻意覆盖新格式 html/csv/pptx；与原 13 个 AI 领域语料构成 21 文档、2508 块的评测库（user 99，经真实入库管线 + 云端 bge-m3 嵌入）。
- 评测集 34 → **103 条**（86 正 + 17 负，其中 4 条跨域陷阱负样本），并重写评测指标（P0.5 修正）：
  - 正样本单独统计 Recall@k / nDCG@k / MRR；
  - 负样本统计 **FalseRecall@k**（误召回率）与 **Balanced**（Recall 与特异度的调和平均）；
  - 输出正/负样本 top-1 分数分布（阈值标定依据）；
  - 新增 `rerank` 模式 = 生产管线形态（hybrid 宽召回 → CrossEncoder 概率重排 → 0.3 阈值），与纯向量/混合可对比。

### 实测发现并修复的问题（按发现顺序）
1. **云端 embedding/rerank 模型名不存在（生产阻断级）**：MySQL 配置 `BAAI/bge-small-zh-v1.5` 在硅基流动并不存在（400 Model does not exist），任何新知识库初始化/上传必失败。已改为实际存在的 **BAAI/bge-m3**（1024 维）；rerank 同样配错（bge-reranker-base），已改 **BAAI/bge-reranker-v2-m3**。这顺带完成了评估清单 P1 的嵌入模型升级。
2. **评测脚本 nDCG 与 Recall 失真**：召回文件名未去重，同文件 5 个 chunk 占满 top-k——nDCG 虚高到 >1，多相关文档 Recall 被虚假压低。已修（去重保序）。
3. **BM25 弱词重叠穿透负样本防线**：「黑洞的信息悖论」仅靠「信息」一词命中提示词文档，经按最大值归一拿到 evidence=1.0 直接通过（H3 证据分设计的盲点）。修复：**BM25 词覆盖率门控**——命中须覆盖查询分词 ≥50% 且含多字词。
4. **分词边界不一致漏检**：查询「逾期」vs 文档 token「逾期费」不相等导致真实命中被门控误杀。修复：门控改用**原文子串匹配**；另补多字疑问虚词停用词（怎么/如何/为什么/什么），分词器升版 v3（旧 BM25 pickle 自动重建）。

### 终版评测结果（k=5，103 条）

| 模式 | Recall@5 | nDCG@5 | MRR | FalseRecall@5 | Balanced |
|------|----------|--------|-----|---------------|----------|
| 向量 | 0.9767 | 0.9758 | 0.9826 | 58.8%（10/17） | 0.579 |
| 混合 | **0.9884** | **0.9841** | 0.9884 | 58.8%（10/17） | 0.581 |
| **rerank（生产形态）** | 0.9767 | 0.9794 | **0.9942** | **5.9%（1/17）** | **0.959** |

### 阈值标定结论（数据驱动）
- **向量分数无法区分正负**：正样本 top1 0.520-0.833（p25 0.574）与负样本误召回 0.500-0.607 严重重叠——`ABSOLUTE_MIN_SCORE=0.5` 只能当廉价预过滤，**不能作为最终防线**（维持现值即可，勿再调高：0.62 会误杀 1/4 正样本）。
- **重排概率是唯一可靠的判别信号**：正样本 p25=0.851 / 中位 0.982，负样本除 1 条对抗样本外全部 <0.25。`SIMILARITY_THRESHOLD=0.3` 作用在重排概率上得到验证；**建议 Web 端把「启用重排」默认打开**。
